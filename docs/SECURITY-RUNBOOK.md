# Security Runbook — Credential Rotation

This runbook covers rotation of the credentials that were stored in plaintext at the repo root
in `spb.md` (gitignored but present on disk). The credentials are believed to have leaked into
the repository worktree only (no git history), but the safe assumption is that they are
compromised and must be rotated.

## 1. Rotate the Supabase database password

1. Sign in to the Supabase dashboard: https://supabase.com/dashboard
2. Select the **AOI** project (`bpggizzqkhgasaikybrf`).
3. Open **Project Settings** → **Database**.
4. Click **Reset database password**.
5. Choose a new password:
   - At least 24 characters.
   - Mixed case + digit + symbol.
   - Generated by a password manager (e.g., `openssl rand -base64 24`).
6. Save the new password into your password manager immediately. Do not store it in any project
   file.
7. Update any local tools that connect to the database directly:
   - `psql` connection strings.
   - `supabase link --project-ref bpggizzqkhgasaikybrf` will keep working because it uses the
     access token, not the DB password.
8. Restart any backend workers or jobs that hold a DB connection pool so they re-handshake.

> **Note**: The browser app never uses the DB password directly — it goes through the
> publishable key + RLS. The DB password is only used by maintenance scripts and the seed
> scripts in `scripts/`.

## 2. Revoke and recreate Supabase Personal Access Tokens (PATs)

Two PATs were leaked. Both must be revoked.

1. Sign in to the Supabase dashboard with your own user account (not the seeded
   `mikerevou@aoitechnology.com` user).
2. Open **Account** → **Access Tokens**.
3. Find the two tokens in the account's access-token list that were created for this project.
4. Click **Revoke** for each.
5. If you need a new token for CLI automation, click **Generate new token** with a scoped
   description (e.g., `aoi-cli-2026-08-07`). Store the new token in your password manager or
   the CI secret store — never in `.env.local`.

The `mikerevou@aoitechnology.com` account password was leaked.

1. In the Supabase dashboard, open **Authentication** → **Users**.
2. Find `mikerevou@aoitechnology.com`.
3. Click the user row → **Send password reset** OR **Set password** (admin override).
4. Use a strong password (≥ 14 chars, mixed case + digit + symbol).
5. Communicate the new password to the user out-of-band (phone call, encrypted message).
6. After the user logs in, instruct them to change it again themselves via the Profile drawer's

> **Important**: Once the SOC fixes below are deployed, the user will also be prompted to set

## 4. Rotate the Supabase service-role key

The service-role JWT in `.env.local` (`SUPABASE_SERVICE_ROLE_KEY`) has a 30-year expiry. This
is excessive and should be rotated regardless of the leak.

1. In the Supabase dashboard, open **Project Settings** → **API**.
2. Locate **Project API keys** → **service_role**.
3. Click **Rotate service role key** (this immediately invalidates the old key).
4. Copy the new key value.
5. Update local `.env.local`:
   ```text
   SUPABASE_SERVICE_ROLE_KEY=<paste-new-key>
   ```
6. Update any CI secrets that store the service-role key (only privileged user workflow uses
   it via the `admin-create-user` edge function — the secret is named `SUPABASE_SERVICE_ROLE_KEY`).
7. Redeploy the edge functions so they pick up the rotated secret:

   ```bash
   supabase functions deploy admin-create-user --no-verify-jwt
   supabase functions deploy survey-public --no-verify-jwt
   supabase secrets set ALLOWED_ORIGINS=https://1abdulkarimmousa.github.io
   ```

8. Verify the deploy:

   ```bash
   curl -X POST https://bpggizzqkhgasaikybrf.supabase.co/functions/v1/admin-create-user \
        -H "Authorization: Bearer $TEST_USER_JWT" \
        -H "Content-Type: application/json" \
        -d '{"action":"create","displayName":"Test Survey","email":"test@example.com","role":"intern"}'
   ```

   Expected: HTTP 403 `Administrator permission is required` (the rotation preserved the
   function but the old JWT no longer authenticates).

After the credentials above are rotated, apply the new hardening migration:

```bash

```

Expected additions:

- Drops the dead `rpc_mark_password_changed` function (it was temporarily granted to

## 7. Verify post-rotation

1. **Login**: Sign in as a normal user. The session should establish with a refreshed JWT.
2. **Password change**: A user who knows their current password should be prompted for it
   before any voluntary password change. The audit change in `auth.js` requires
   `currentPassword` for the non-recovery path and verifies it via a temporary Supabase client
   before calling `auth.updateUser`.
3. **Edge function embed check**: Visiting a survey embed from an unlisted origin should return
   HTTP 403 with code `SURVEY_EMBED_ORIGIN_DENIED`. The body-provided `embedOrigin` field
   is no longer honored.
4. **Service role key**: Any old client still calling edge functions with the rotated JWT
   receives HTTP 401.
5. **Database**: Old DB password no longer connects via `psql`.
6. **Help center** and **workspace**: Pages load with no security-related console errors.
